The user asked for VS Code–style theming where *everything* is customizable from files, so they can ask Claude
Code to restyle Tern for them. They said "keep the current look as the default" and "consistency first", then
"just do it, don't ask me". Work was split into three parts:

1. **Consistent UI** — done
2. **Settings and themes in files, applied live** — done
3. **In-app theme picker** (⌘K ⌘T, preview while moving through the list) — done
4. **Per-element styling, tokens, background images** — done (see Part 4)
5. **Everything open + light/dark for terminal programs** — done (see Part 5)

Everything below is **uncommitted** on `main` (working tree). Tests pass (`cargo test --workspace`), clippy and
`cargo fmt --check` are clean. The user has not reviewed the diff or asked for a commit yet: ask before
committing, and branch first (rule: don't commit on `main`).

## Part 2: settings and themes

`crates/tern-app/src/settings.rs` (new). Config dir is `crate::dirs::config()`: `~/.config/tern` (macOS and
Linux, honors `XDG_CONFIG_HOME`), `%APPDATA%\Tern` (Windows).

- `settings.json` (user): `theme`, `ui` (font), `editor` (font), `terminal` (font, line height, `colors`),
  `layout` (sizes, radius), `colors` (UI color overrides by gpui-component theme key). `deny_unknown_fields`
  everywhere, so typos are errors.
- `themes/*.json` (user): gpui-component `ThemeSet` format; each theme may add a `terminal` palette (named keys:
  `background`, `foreground`, `cursor`, `selection`, `dim_foreground`, `black` … `bright_white`).
- Written by Tern on every start: `settings.schema.json` (schemars; color keys come from gpui-component's
  `ThemeConfigColors`), `README.md`, `reference/tern-dark.json` and `reference/tern-light.json`.
- Built-in themes: **Tern Dark** (gpui-component Default Dark plus Tern's palette) and **Tern Light** (Default
  Light plus a One Light ANSI palette; only lightly checked).
- Watched with `tern_fs::FsWatcher` (100ms debounce) → `load()`. If a file can't be read, the last applied
  settings stay and the reason shows in the status bar (`SettingsStatus` global, right side of the workspace
  status bar).
- Terminal palette precedence: `settings.terminal.colors` > theme's `terminal` > derived from the UI theme's
  background/foreground > dark or light default.
- `TerminalLook` global (in `terminal_view.rs`): font plus `Arc<Palette>`. Each `TerminalView` syncs to it in
  render and prepaint (`sync_look`), and a font change resets cell metrics, which resizes the PTY.
- The daemon answers OSC 4/10/11 color queries from `tern_mux::paths::palette_path()` (`mux_dir()/palette`),
  which the app writes on each load. `tern_term::palette::PaletteFile` re-reads it when its mtime changes. This
  was verified: light theme → `rgb:ffff/ffff/ffff`.
- `cx.set_window_appearance(...)` makes the native macOS title bar follow the theme mode.

Not configurable (documented in the README): bar and tab height (fixed by gpui-component's `Tab`); editor line
height. Panel sizes only apply to panels opened afterwards.

## Part 4: elements and tokens

The user asked that every element have its own properties (padding, colors, …) so nothing is locked together, and
to tie elements to a shared variable only when they want them consistent; then background images.

- `style.rs` now holds `TOKENS` (shared values: `row_height`, `bar_height`, `text_sm`, `bar_background`, `git_added`,
  …) and `ELEMENTS` (each element, e.g. `explorer.row`, `workspace.status_bar`, `vertical_tabs.group`, `terminal`, with
  its properties and defaults; property groups `ROW`, `HEADER`, `PANEL`, `IMAGE` are shared between alike elements).
  Defaults point at tokens or theme colors, so the default look is unchanged.
- `settings.json` gets `tokens` (override built-ins or add your own) and `elements` (`{"explorer.row": {"height":
  26}}`). The old `layout` key is gone (it was never released): its sizes are tokens/element props now, `radius` and
  `radius_lg` are tokens that also feed the component theme.
- Values: number = px, `"Npx"`, `"Nrem"`, colors (incl. `transparent`), text, or `"$name"` → user token, built-in
  token, another element's property (`$explorer.row.height`), or theme color by theme-file key (`$muted.foreground`)
  or field name. Inside token X, `$X` means the theme color X (so `"border": "$border"` works). Loops, wrong kinds,
  unknown elements/props/tokens go to the status bar; the property keeps its default.
- Resolved in `settings::load` after the theme is applied (`style::resolve` → `Looks` global); code reads
  `style::el("name", cx)` → `.len/.px/.color/.num`, `.apply(div)` (box props), `.backdrop()` (image layer).
- Element names must not equal a theme color key's prefix+prop (test); hence `pane_tab_bar` and
  `workspace.status_bar`.
- Background images on `window`, `workspace`, `explorer`, `changes`, `scratches`, `vertical_tabs`, `terminal`:
  `background_image` (path relative to config dir, `~/`, or absolute), `_fit`, `_opacity`. They show through only where
  the front is see-through: `panel_background` with alpha, `terminal.background_opacity` < 1.
- Tern writes `reference/elements.md` (every token/element/default) and puts them in `settings.schema.json`.
- Checked in the debug build: default look unchanged; `row_height` token moves explorer + scratches rows while a
  `changes.row` override stays; workspace image through translucent panels and terminal; typo error in status bar.
- Not covered: gpui-component internals (Tab, Button, inputs, menus) only follow theme colors; editor body has no image.

## Part 6: stuck daemon fix, Restart Background Terminals

- Bug: ending a terminal (`Host::kill` → `hang_up`) blocked in `waitpid(pid, 0)` while the program, on its way
  out, waited for its last output to be read from the tty; nothing read it → host thread and program stuck forever
  (`ps` state `E`), the session never left the list, so the daemon never went idle and never updated. Seen live:
  8 host threads in `__wait4`. Fix: `hang_up` drains the master while polling `WNOHANG`, SIGKILL after the grace,
  gives up after a second grace and `abandon`s the driver (forget, so the Pty's blocking drop never runs). Test
  `kill_ends_a_program_that_writes_on_its_way_out` hangs without the drain, passes in ~3s with it.
- Claude Code 2.1.301 picks light/dark from `COLORFGBG` at start only (probed: OSC 11 alone → dark; a `?997`
  report while running → no change). So a theme change reaches new Claude tabs only.
- `restart.rs`: Tern ▸ Restart Background Terminals… (Help menu off macOS): confirm dialog, then
  `Connector::stop_server` kills the daemon by the pid from its Hello (works on old daemons), SIGTERM then
  SIGKILL (taskkill on Windows). Terminals that lose it within 15s start afresh on the new daemon. Debug control
  command `restart-background`. Verified in the debug build.
- Installed with `scripts/install-macos.sh` (Developer ID signature).

## Part 7: stale daemon after a reinstall

- The user saw Claude Code still dark on Tern Light. Cause: the daemon (`tern --server`) had started at 01:20, before
  the 13:23 install, so it still ran the old code: no `COLORFGBG`, no ?996 answers. The status bar said
  "background: ✓" because both are 0.2.2.
- `tern_mux::paths::build_id()`: a hash of the executable's bytes, taken at start (`serve`, `Connector::new`). Sent as
  `build` in the server `Hello` (`serde(default)`, so old daemons send ""). `Connector::server_same_build()`; the
  status bar shows "background: an older build (updates once its terminals end)", and the restart dialog mentions it.
- `scripts/install-macos.sh` now quits Tern (osascript), kills the daemon (TERM, then KILL) and reopens Tern, detached
  with nohup (the script may run in one of those terminals). `TERN_KEEP_RUNNING=1` skips it. It uses `ps` + `awk`, not
  pgrep: macOS pgrep skips its own ancestors, and the daemon is one. Its check mode was tested; the full restart wasn't run.
- In-app updater (`update.rs`), as the user asked ("on the new version kill everything; tell the user, they confirm,
  then install"): the offer dialog says the background terminals restart too and how many terminals run now
  (`restart::running`); after staging, `stop_terminals_and_quit` saves the session, sets `quitting`, runs
  `Connector::stop_server` (works on old daemons: pid from Hello), then quits. Tabs start again at the next launch;
  Claude tabs `--resume`. Not run end to end: the updater only works in an installed app with a newer release.

## How to see the app (the user asked to verify visually)

The shell Claude Code runs in inherits the installed Tern.app's Screen Recording permission, so `screencapture`
works. To capture just a window, find its ID first:

```swift
// winid.swift — swiftc -O winid.swift -o winid; ./winid tern-app
import CoreGraphics
let owner = CommandLine.arguments.count > 1 ? CommandLine.arguments[1] : "tern"
let list = CGWindowListCopyWindowInfo([.optionAll], kCGNullWindowID) as! [[String: Any]]
for w in list {
  let o = (w[kCGWindowOwnerName as String] as? String) ?? ""
  let layer = (w[kCGWindowLayer as String] as? Int) ?? -1
  let b = w[kCGWindowBounds as String] as? [String: Any] ?? [:]
  if o.lowercased().contains(owner.lowercased()) && layer == 0 && ((b["Height"] as? Double) ?? 0) > 100 {
    print(w[kCGWindowNumber as String]!, o, b["Width"]!, b["Height"]!)
  }
}
```

Then `screencapture -x -o -l <id> out.png`. This works even when the window is covered, and the debug build
needs no permission. For pixel colors, a few lines of Swift with `NSBitmapImageRep.colorAt` work. Note that
captured colors shift slightly (`#0a0a0a` reads as `#0d0d0d`, `#171717` as `#1e1e1e`).

To run a debug build without touching the installed app's session or the user's real config:

```sh
cargo build -p tern-app
XDG_CONFIG_HOME=<scratch>/xdg scripts/dev-app-macos.sh <folder>   # prints the pid; window owner "Tern Dev"
printf 'state\n' | nc -U -w 2 target/dev.sock      # commands: see crates/tern-app/src/control.rs
```

Control-socket coordinates are about **22px higher** than in the capture: click at `y_capture - 22`. Useful
commands: `ws-open PATH`, `file-open REL`, `key cmd-shift-t` (shell tab), `term-type TEXT\n`, `term-screen`,
`rclick X Y`, `key escape`.

## Part 9: debug build has its own identity

- The user: every install, both the debug and the installed Tern lost their privacy permissions. A bare
  `target/debug/tern-app` is ad-hoc signed (new identity each build) and, run from Tern's terminal, macOS holds
  Tern.app responsible for it. The installed app had also been signed once with Developer ID, once with Apple
  Development; each switch changes its designated requirement, so macOS asks again.
- `scripts/dev-app-macos.sh`: wraps the debug build as `target/debug/Tern Dev.app` (`dev.tern.debug`, no URL
  scheme or document types), signs it with the Apple Development identity (re-signs only when the build changed),
  launches it with `open -n --env TERN_CONTROL=<abs> [--env XDG_CONFIG_HOME, TERN_SESSION]`, prints its pid.
  `scripts/dev.sh` uses it on macOS. Verified: DR `identifier "dev.tern.debug" and ... Apple Development`, ppid 1.
- `scripts/install-macos.sh` warns when the new signature's designated requirement differs from the installed one.
- Tern Dev needs Screen Recording granted once (System Settings), then it stays across rebuilds.
