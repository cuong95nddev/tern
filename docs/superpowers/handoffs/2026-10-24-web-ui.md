# Handoff: Tern's panels on the web, with per-device permissions (2026-10-24)

## What the user asked

"Can Tern support a TUI version so it can be used on the web without rewriting much?" After discussing it, the user
chose: **a web UI served by `tern --web`, with the data read by Rust in a shared crate (option A below)**, and **per-device
permissions** for paired browsers. Nothing is designed in detail or built yet; the next session starts with
brainstorming → spec. Talk to the user in Vietnamese; code and comments in English.

## Why not a TUI

- The backend crates have no GPUI: `tern-term` (~5.5k lines, alacritty_terminal), `tern-mux` (~5.8k), `tern-fs` (~2.5k),
  `tern-bridge` (~1.2k). The UI, `tern-app` (~40k lines), is GPUI throughout, so a TUI rewrites the whole view layer anyway.
- A TUI loses what the desktop has (kitty images, pixel scrolling, Markdown preview with images), cannot get ⌘ keys,
  and its template renderer would map px styles to cells badly.
- The web renders the same things better: the templates' flex/colors/borders/radii map to HTML/CSS directly, and
  terminals already work there with xterm.js. A TUI is only worth it later, for plain SSH use.

## How things run today

Three processes:

1. **Daemon** (`tern-mux`): owns the PTYs and sessions. Never listens on the network.
2. **Desktop app** (`tern-app`, GPUI): the UI, and today also where usage, CPU/memory, resources and agents are read.
3. **`tern --web`** (`tern-web`): its own process, talks **only to the daemon** (a viewer connection per page,
   `crates/tern-web/src/bridge.rs`), serves `assets/` (xterm.js). Page → server messages: `View`, `Leave`, `Drive`,
   `Input`, `Resize` (`FromPage`). So the web can show terminals and nothing else.

## Decision: option A, a shared crate

Move the data reading out of `tern-app` into a crate without GPUI (working name `tern-core`; check the name with the
user). The desktop app and `tern --web` each call it and read for themselves, so the web keeps working while the
desktop app is closed (the daemon stays up). Rejected: B, the web asking the desktop app (dies with the app, needs a
new channel).

What moves, per module (line counts today):

| Module | What goes to the shared crate | What stays in `tern-app` |
|---|---|---|
| `usage.rs` (789) | `Limit`, `Pace`, `Report`, `Cached`/cache files, `read`/`ask`/`credentials`/`keychain`/`get`/`parse`, timing consts, `countdown`/`ago` | `UsageStore` entity + `Global`, refresh scheduling via `cx` |
| `accounts.rs` (~460) | `Account`, load/save, dirs, `email`, `keychain_service`, `prepare`, `alive` | `AccountStore` entity + `Global` |
| `system.rs` (215) | `Ticks`, `cpu_ticks`, `memory` (mac/linux/windows), `gigabytes` | `SystemStore` entity, sampling timer |
| `resources.rs` (549) | `Proc`, `Usage`, `Table`, `Sampler`, `scan` per OS, `parse_stat`, `attribute` (generalize its `TabsOf` input), `bytes`/`percent` | `ResourceStore` entity |
| `agents.rs` (457) | `Agent` detection, `ContextUse`, `ContextGuard`, `priority`, `display_name`, labels, logo bytes | `status_look`/`status_color`/`ring_vars` (use `Theme`/`Hsla`) |
| `file_tree_view.rs` (981) | little: `tern_fs::tree`/`ops`/`watch`/`git` already hold the logic | the view |

Pattern to keep: the shared crate gives plain data + "read now" functions; each process owns its own timer/store.
The stores in `tern-app` become thin wrappers. Do this refactor first, with no behavior change, as its own commit.

Points to settle while designing:

- **Workspaces.** Resources group terminals by workspace, and only the desktop app knows workspaces/tabs. The web can
  read the saved session (`window_state::load_session`, file under `dirs::data()`), which needs `SavedWindow` etc. in
  the shared crate too, or group by session only. The same question decides how the web lists workspaces at all.
- **Keychain.** `usage` reads the Claude sign-in from the login keychain. `tern --web` is the same binary, but verify
  that macOS does not prompt when the web process reads it.
- **Two readers.** Usage has rate-limit/backoff rules (`REFRESH`, `RATE_LIMITED`, `ERROR_BACKOFF`). With two processes
  reading, share the cache file (it already exists per account) so they don't double the calls.

## Web UI

- Render the templates (`templates.json` + user overrides) to HTML/CSS in the page, so the web follows the same
  structure and theme; behavior (`frame`/`slot`) is written again in JS. This was proposed, not explicitly
  confirmed by the user: confirm in brainstorming. CLAUDE.md requires new UI to go through the template engine.
- Server → page: new message types next to the terminal ones (usage, system, resources, agents, tree rows, git
  changes), pushed on change. Page → server: new requests (expand dir, open file, file ops, refresh usage…).
- First version scope to agree on (suggested): terminals (existing) + agents list + usage + system/resources +
  explorer (read, then write) + changes (read). Not in v1: diff editing, commit, settings, layout editing.

## Per-device permissions

Today every paired device (`crates/tern-web/src/access.rs`, `web-access.json`) can do everything: view and drive
every terminal. Proposal to refine with the user:

- A role (or flags) on `Device`, chosen when making the pairing link in Settings ▸ Connections and changeable there
  later. Candidate levels: **view** (watch terminals, usage, system, read files), **drive** (also type into terminals
  / take control), **files** (also create/rename/move/trash files), maybe **commit** later.
- Enforce on the server for every message (`bridge.rs` and the new handlers), never only by hiding UI. Send the
  device's role in `hello` so the page hides what it may not do.
- Stored like the rest of `Access` (serde default for old files). Open question: what existing paired devices get
  (full rights = today's behavior, or view and re-grant).
- Revoking a right should end/downgrade open pages at once, like revoking a device does now (`WATCH`, 1 s).
